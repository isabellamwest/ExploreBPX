# Explore_BPX — UI Framework

This document defines the **application-wide UI framework**: the shell layout,
the responsibilities of each pane, the global navigation model, common
interaction principles and keyboard conventions, and the global constraints every
feature must follow.

It deliberately does **not** describe individual feature behaviour. How a specific
feature behaves within this framework — the SearchPopup, the editing cards,
keyboard navigation of issues, the Issues tab, authoring workflows — lives with that
feature in [03-features.md](03-features.md). Architectural boundaries and the
navigation service contract live in [01-architecture.md](01-architecture.md).

Design rationale is embedded inline with the decision it explains.

## UI Philosophy

Explore_BPX presents a fixed, familiar editor-style shell rather than a wizard or
dashboard. The product-level philosophy is stated in [00-project.md](00-project.md);
its UI consequences are:

- BPX objects and parameters remain visible as a stable hierarchy.
- Search and validation navigate to locations; they never filter or replace the
  structure.
- Secondary information is available on demand without permanently occupying
  workspace.
- Editing works against the raw working document, so invalid work-in-progress
  data can be represented and corrected.

## Workspace Layout

The workspace uses a fixed multi-pane shell with familiar editor conventions:

```text
[top context bar spans the main content area]
[activity bar] | Tree | Parameter list | Inspector
[bottom status bar]
```

The main Editor workspace is a three-pane master-detail-detail layout:

- **Tree** — navigable BPX objects.
- **Parameter list** — the direct parameters of the selected object.
- **Inspector** — the selected parameter's workspace for viewing and editing.

All three panes remain visible while editing, so sibling context is preserved. A
selected object does not replace the tree, and a selected parameter does not
replace the parameter list. The panes sit flush against one another, separated
by a single 1px hairline seam (the splitter handle itself) rather than a
gutter plus a bordered pane edge.

**Rationale.** A fixed three-pane master-detail shell keeps object → parameter →
editor context visible at once and matches familiar IDE conventions, giving each
band one clear job. The alternatives — a two-pane body-swap, a dockable
inspector, or a floating document-info card — either hide sibling context or add
layout complexity without benefit. The cost is horizontal-space pressure from
three columns and a top bar that shows location rather than acting as clickable
navigation. The activity bar and Inspector are the seams that absorb future
workspaces and parameter-centric tools without reworking this layout.

## Panes and Shell Surfaces

### Activity bar

The activity bar switches the full content area between top-level workspaces:
a narrow VS Code-style icon rail, each entry an icon-only glyph whose name is
discoverable via a hover tooltip (and exposed to accessibility tools). The
current workspaces are:

- **Workspace** — document-level information and management: opening a file,
  creating a new document from a model skeleton, and current-document info. It
  is the app's default landing page when nothing is open.
- **Editor** — the main tree/list/inspector workspace. It renders the current
  *Workspace* (see [00-project.md](00-project.md)); today that is always a single
  document, and it grows to render a Primary and optional Reference document
  additively rather than switching into a separate compare mode.
- **Diagnostics** — the active document's Issues and Outstanding (completion)
  lists (see [Diagnostics page](#diagnostics-page) below).

The Diagnostics icon carries no colour or symbol of its own — no tick, no
warning triangle — since it must assert neither pass nor fail. A small pill
badge at its bottom-right corner carries that state instead: it shows the
combined error+warning count of the Diagnostics page's **Issues** section
only (see [Diagnostics page](#diagnostics-page) below) — a diagnostic the page
has absorbed into Outstanding never contributes to the badge, and a `float_type`/
`int_type` pair counts once, matching the one row it renders as. It is red
only when at least one *error* is present, amber for warnings-only. A fresh
skeleton, or a document whose only gaps are expected fields the app itself
added and left empty, shows no badge at all: **red means wrong, never
unstarted**. The activity bar otherwise uses no colour: the selected entry is
distinguished only by a left accent stroke and a stronger icon tone, keeping
colour reserved for validity state throughout the shell (see
[00-project.md](00-project.md)).

The activity bar is reserved for **major workspaces that replace the main content
area**, such as Workspace, Editor, Diagnostics, and a future Database workspace.
Comparison is deliberately **not** a separate activity-bar workspace: it is a
capability of the Editor when a Reference document is present, not a mode.
Parameter analysis, documentation, graphs, statistics and similar secondary tools
are **not** activity-bar workspaces; they belong in the Inspector. Only shipped
workspaces appear; disabled placeholders for future workspaces are not shown.

**Rationale.** Most future workspaces are full-area pages, so a vertical rail
scales better than top tabs and gives validation state a natural badge home. Top
tabs, a VS Code-exact sidebar-only switch, or menu-driven switching were rejected
as less scalable or less honest. The cost is relatively heavy chrome for only
three current workspaces and the need for an icon set. Database can later be
added without layout rework.

### Page header

A thin bar above the workspace stack shows the active page's name in small
upper-case type — the one place a page's name is written out, since the
activity bar's own entries are icon-only.

### Top context bar

The top bar communicates the current document's identity: an elided label
reading `Title · BPX vX.Y` (either segment omitted when absent; the full text
is always available as a tooltip). It is a context surface, **not** a
clickable breadcrumb — the always-visible tree and parameter list already
provide structural navigation — and hosts no feature modes; all navigation
routes through `NavigationService` ([01-architecture.md](01-architecture.md)).

The declared model is deliberately **not** shown here. `Header.Model` is an
ordinary enum field, edited in the Editor like any other parameter — its
commit routes through `ChangeModel`, which also adds the target model's
required-but-missing sections in the same undo step (see
[Editing](03-features.md#4-editing)). An earlier build carried a Model chip in
this bar, a menu button that committed the same field; it was removed as a
second door onto an edit the Editor already offers, and because a per-document
field does not belong in the window's chrome.

### Tree pane

The tree contains BPX objects only, never individual parameters. Selecting an
object updates the parameter list. Validation markers in the tree appear on the
lowest visible object containing an issue; ancestors do not duplicate the marker
once the relevant branch is open.

The tree is also where document *structure* is edited, via a right-click menu
on the node it lands on. The schema fixes the hierarchy, so the menu offers
only its real degrees of freedom — nothing disabled, nothing invented:
**Add section ▸** lists the schema-expected child sections absent from the
node (right-clicking empty space addresses the document root — how the
optional top-level State/Validation are added; electrode sections resolve
their single/blended union from live content, not a guess). **Add material…
/ Add experiment…** appear on the two dict-keyed containers whose children
the user names, via an anchored name popup (Enter confirms; a sibling's name
is refused with the reason inline). **Add subsection…** appears on the open
`User-defined` bucket and any subsection within it — the one place the schema
(`additionalProperties: true`) lets the user name sections freely, nested
without limit; its user-authored sections carry a plain **· custom** tag in
the tree so they read apart from the fixed schema sections. (Free-form
*parameters* go into a User-defined section the usual way — the parameter
list's **+ Add parameter**, which accepts a custom name there — not the tree
menu.) **Rename…** appears only on user-named keys
(materials, Validation runs, and User-defined content) — schema property
names are never editable. **Remove / Remove section** covers everything structurally
removable, required sections included (the validator reports the damage);
removing a populated target asks first, an empty one removes instantly, and
either is one undo step.

### Parameter list pane

The parameter list shows the direct parameters of the selected object.
Selecting a parameter updates the Inspector. Each row carries a right-aligned,
fixed-pitch **value preview** — verbatim committed values, a ghosted "—" for
`null`, a ghosted data-derived summary for Inspector-only kinds ("table · 3
points") — that is deliberately **read-only**: a 2026-07-15 design pass on
inline quick inputs concluded the scanning value lay in seeing values, not a
second editing surface; editing stays in the Inspector's per-kind cards.

A **+ Add parameter** header above the list opens a popup for adding a
parameter to the selected object; actions on an *existing* row (**Remove
parameter**) live in that row's right-click menu instead. This is the
app-wide convention: context menus never create at row level, only at
container level (the tree's Add section/material/experiment/subsection). The
+ Add parameter button is also how free-form parameters enter a User-defined
section (a typed custom name), since that bucket declares no schema fields.

A row whose committed value is `null` renders muted/grey (name and unit both)
so emptiness reads at a glance. The trailing **⚠** marker mirrors the
Diagnostics page's post-absorption Issues (see
[Validation](03-features.md#5-validation) and
[Authoring](03-features.md#8-authoring)): an Expected field's calmed `null`
renders grey with no ⚠, a custom parameter's uncalmed `null` renders grey
**with** ⚠. A parameter's own Inspector badge and Issues tab are unaffected —
they report the validator verbatim regardless of what the list row shows.

A collapsed **`▸ N fields to add`** line sits at the end of the real rows
whenever the section has schema-Expected fields with no entry in the document
(any Expected field, not Required-only); expanding it lists each missing
alias as a `+ name` row tagged like the add-parameter popup's own Suggested
rows (see [Authoring](03-features.md#8-authoring) for the query and command
behind it). The group is suppressed under an undeclared/unrecognised model
except for `Header`, whose fields don't vary by model and whose `Model`
suggestion is where a model gets declared.

### Inspector pane

The Inspector is the selected parameter's work surface and the primary home for
all parameter-centric tools. It is split top-to-bottom into two areas:

- a **primary editing area** at the top, hosting the value editor **Edit**
  controls; and
- a collapsible **secondary workspace** at the bottom — a tab strip over a
  collapsible panel — hosting parameter-centric tools. In current scope it
  contains the **Issues** and **Documentation** tabs (`inspector.py`); future
  workflows (Analysis, References) are added as further tabs over the same
  selected `ParameterItem`, not as separate pages or activity-bar workspaces.

For bulk work on large values (interpolated tables, experiment series), the
primary editing area supports an **expanded editor**: a text **Expand** action
on the grid's toolbar grows the grid to fill the Inspector pane (the secondary
workspace collapses to its tab strip to make room), *within the Inspector
pane* — never a floating window — and **Collapse** restores the compact card.
The tree and parameter list stay visible and interactive throughout. The
convention this sets: **in-place takeover is for editing; floating dialogs are
reserved for read-only visualisation** (see Analysis in
[03-features.md](03-features.md)).

A vertical splitter sits **above** the tab strip, resizing tabs and panel
together. The secondary workspace is **workspace state, not parameter
state**: its expanded/collapsed state, active tab and panel height persist
across parameter changes, refreshing the active tab's content rather than
opening/closing on selection. It collapses automatically only when no
parameter is selected (visibility only — intent and active tab are restored
once one is); otherwise only the user collapses it, by clicking the active
tab again.

**Rationale.** Secondary information should be reachable on demand without
permanently occupying workspace. Keeping parameter-centric tools in the
Inspector prevents activity-bar sprawl and keeps those tools next to the
parameter they describe. A single collapsible tabbed workspace — rather than
a right-side dock, inline accordion sections, or a permanent auxiliary panel
— keeps the tools together with simple, predictable open/closed state.

#### Parameter documentation: popover vs. Documentation tab

Parameter documentation is split by depth. The ParameterCard's ( i )
affordance opens a transient **popover** for the quick glance (symbol,
meaning, units, accepted types, ontology link): it opens from the card and
closes on Escape, on a press outside it (consumed — see the keyboard and
dismissal conventions below), on application deactivation, or on a second
( i ) click, and is destroyed with its card so changing the inspected
parameter cannot leave it describing the wrong one. The secondary workspace's
**Documentation** tab carries the multi-paragraph technical prose instead,
persisting beside the editor rather than dismissing on the first outside
click — appropriate for page-long content the popover was never meant to
hold. Both are fed by the unified parameter-metadata provider (see the seam
in [01-architecture.md](01-architecture.md)).

### Diagnostics page

The Diagnostics activity-bar workspace is a summary strip over a
fixed-width section rail beside a detail pane (`ui_qt/diagnostics_panel.py`;
`core/page_buckets.py` supplies the one shared grouping the strip, rail and
pane all render from, so they cannot disagree). The **strip** shows
error/warning/outstanding totals; each chip is also a view-only filter
toggle (left-click mutes that category's rows in the pane; the chip greys
out), and a text field on the strip's right filters rows live by
case-insensitive substring against what each row shows (location/name and
message). Filtering never changes any count anywhere — strip totals, rail
badges, box headers and the app badge keep reporting unfiltered truth, the
pinned ✓ empty states never render over merely-hidden rows, and a single
muted "N hidden by filters" line at the view's end accounts for what the
filters hid (fold-hidden rows are not counted — folds aren't filters).
Filter state is per-session and resets on a new document. The **rail** lists "All sections" (one
neutral total badge, the default selection), a separator, then one entry
per section — present or not — in document order; a Document bucket
(diagnostics/tasks that resolve to no existing section) appears first only
when occupied. Badges are quiet: a clean section shows none at all, red/amber
count badges appear only for nonzero errors/warnings, a grey badge for
outstanding work, and an absent section renders its name italic. Clicking a
rail entry or moving the arrow keys switches the pane immediately and never
touches the document.

The **detail pane** is either one selected section's Issues and Outstanding
group boxes (each a bordered card with a banded header — Issues carries its
own red/amber badges, Outstanding's header carries the "N of M remaining"
ratio) or, for "All sections", the whole-document backup view: every bucket
exactly once, a foldable header (same badges as the rail) over its issue
rows then its outstanding rows. Row layout, the absorption rule and the
badge-derivation architecture are specified in
[Validation](03-features.md#5-validation); this page renders that same
model, grouped into rail sections, not a second source of truth for it. The
activation contract is shared with the Issues tab (select ≠ act;
Enter/double-click navigates); rail selection is pure page navigation, not
document navigation, so it alone never acts either.

### Status bar

The bottom status bar communicates document-level state such as source and
modified/saved status. This keeps persistent file state out of the top context
bar, whose role is location and mode.

### Toolbar

The top bar (`main_window.py`) carries document identity on the left and, on
the right, only: **Save** (writes back to the current backing file),
**Export** (writes a copy to a chosen path/format), **Undo**, **Redo**, and
**Search**. It carries no Open/Import action — opening a file lives on the
Workspace page's **Open File** button (`workspace_panel.py`), not the toolbar.

**Undo** reverts the last committed change and navigates to the change it
reverted, rather than leaving the user wherever they happened to be; greyed
when there is nothing to revert. The button is a document action and ignores
keyboard focus. `Ctrl+Z` is bound separately and is focus-aware: it undoes a
focused text editor's own typing first, does nothing while a focused card
holds an uncommitted draft, and undoes the document otherwise (see the
Editing section of [03-features.md](03-features.md)). **Redo** mirrors Undo
exactly, with `Ctrl+Y` (and `Ctrl+Shift+Z`, wherever not already the
platform's own Redo binding) as its focus-aware shortcut.

Unimplemented future actions do not appear as disabled buttons.

**Rationale.** A minimal, honest toolbar keeps controls meaningful; disabled
future buttons and conflated actions were rejected. Export is the seam that
later generalises to simulator hand-off. The precise semantics of Save versus
Export are a feature concern, specified in the Save and Export section of
[03-features.md](03-features.md).

## Navigation Model

All navigation is coordinated by the single `NavigationService`, whose service
contract (resolve path → update state → emit one notification) is defined in
[01-architecture.md](01-architecture.md). This section defines the **UI side**: how
views react to a navigation notification.

On each navigation notification, views collectively:

- expand the tree to the destination object and select it;
- select the parameter when the target is parameter-level;
- update the context bar;
- scroll the relevant destination into view;
- apply a temporary highlight to the destination.

Each view owns the reveal of its own part of the target; no component implements
its own competing navigation behaviour. Feature consumers (Search, Diagnostics
review, and future Compare and reference links) request navigation by target path
and never drive widgets directly.

## Interaction Principles

These principles constrain every feature equally:

- Search and validation navigation must use `NavigationService`.
- Search navigates; it does not filter or hide structure.
- Guidance (validation, and later completion) informs; it does not lock the
  editor.
- Invalid edits may be committed to the raw working document.
- Parameter-centric tools are tabs in the Inspector secondary workspace, not
  activity-bar workspaces.
- The navigable BPX structure is never filtered — including by document
  ownership; ownership is shown through indicators, not by hiding hierarchy.
  Filtering applies only to derived views (Issues, Search results, Analysis
  summaries, future comparison reports), which interpret the structure rather
  than define it.
- UI controls appear when their workflows exist, not as disabled placeholders.
- Creation is offered by visible affordances; actions on an existing row or
  node (remove, rename) are offered by that row's context menu.

## Keyboard Conventions

Keyboard behaviour follows common desktop conventions. The framework-level
conventions are:

- Transient UI closes on Escape before state is cleared or focus returns.
- Enter commits the active editor card; Escape reverts its uncommitted draft.
- Search is focused by both `Ctrl+F` and `Ctrl+P`, and focusing search selects
  existing text.
- Popups anchored to a triggering control (SearchPopup, the add-parameter popup)
  follow the same pattern: Down/Up move the selection, Enter activates it, and
  Escape is staged (clears typed text first, then closes the popup).
- **Dismissal is uniform across every transient popup** — SearchPopup, the
  add-parameter popup and the parameter information popover. A mouse press
  outside the popup dismisses it, and that press is **consumed**: it does not
  reach the control beneath, so one click closes and a second click acts. This is
  the convention menus and command palettes follow everywhere. Application
  deactivation also dismisses. A press *inside* the popup, or inside a control it
  declares as its own (the search box, for its results list), neither dismisses
  nor is consumed. Dismissal is deliberately not driven by keyboard focus alone:
  focus does not move when the user presses a non-focusable surface such as the
  top bar or the page header, so a focus-driven rule would leave popups
  stranded open.

Feature-specific keys (search result navigation, keyboard navigation of issues)
are specified with their feature. As the UI matures, focus order and screen-reader
naming should be checked for the activity bar, SearchPopup, the issue lists and
editor cards.
