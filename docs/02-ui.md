# Explore_BPX — UI Framework

The **application-wide UI framework**: the shell layout, the role of each pane,
the navigation model, and the interaction and keyboard conventions every feature
follows. It deliberately does **not** describe pixel-level styling or individual
widget internals — those live in the code. Architectural boundaries and the
navigation-service contract are in [01-architecture.md](01-architecture.md).

## UI Philosophy

Explore_BPX presents a fixed, familiar editor-style shell rather than a wizard or
dashboard:

- BPX objects and parameters remain visible as a stable hierarchy.
- Search and validation navigate to locations; they never filter or replace the
  structure.
- Secondary information is available on demand without permanently occupying
  workspace.
- Editing works against the raw working document, so invalid work-in-progress
  data can be represented and corrected.

## Workspace Layout

The workspace uses a fixed multi-pane shell with familiar editor conventions:

```text
[top context bar spans the main content area]
[activity bar] | Tree | Parameter list | Inspector
[bottom status bar]
```

The main Editor workspace is a three-pane master-detail-detail layout:

- **Tree** — navigable BPX objects.
- **Parameter list** — the direct parameters of the selected object.
- **Inspector** — the selected parameter's workspace for viewing and editing.

All three panes remain visible while editing, so sibling context is preserved: a
selected object does not replace the tree, and a selected parameter does not
replace the parameter list.

**Rationale.** A fixed three-pane master-detail shell keeps object → parameter →
editor context visible at once and matches familiar IDE conventions. The activity
bar and Inspector are the seams that absorb future workspaces and
parameter-centric tools without reworking this layout.

## Panes and Shell Surfaces

### Activity bar

A narrow VS Code-style icon rail that switches the full content area between
top-level workspaces (icon-only glyphs, names via hover tooltip). Current
workspaces:

- **Workspace** — document-level information and management: opening a file,
  creating a new document from a model skeleton, current-document info. The
  default landing page when nothing is open.
- **Editor** — the main tree/list/inspector workspace. It renders the current
  *Workspace* (see [00-project.md](00-project.md)); today always a single
  document, growing to render a Primary and optional Reference additively rather
  than switching into a separate compare mode.
- **Diagnostics** — the active document's Issues and Outstanding (completion)
  lists (see [Diagnostics page](#diagnostics-page)).

The Diagnostics icon asserts neither pass nor fail: it carries no colour of its
own, and a small badge shows the combined error+warning count of the Diagnostics
page's **Issues** section only — red when at least one *error* is present, amber
for warnings-only. A fresh skeleton, or a document whose only gaps are expected
fields the app itself added and left empty, shows no badge: **red means wrong,
never unstarted**. Colour is reserved for validity state throughout the shell.

The activity bar is reserved for **major workspaces that replace the main content
area** (Workspace, Editor, Diagnostics, a future Database workspace). Comparison
is deliberately **not** a separate workspace: it is a capability of the Editor
when a Reference document is present. Parameter-centric tools (analysis,
documentation, graphs) belong in the Inspector, not the activity bar. Only
shipped workspaces appear; disabled placeholders are not shown.

### Page header

A thin bar above the workspace stack shows the active page's name in small
upper-case type — the one place a page's name is written out, since the activity
bar's entries are icon-only.

### Top context bar

Communicates the current document's identity: an elided `Title · BPX vX.Y` label
(either segment omitted when absent; full text as a tooltip). It is a context
surface, **not** a clickable breadcrumb — the always-visible tree and parameter
list already provide structural navigation — and hosts no feature modes; all
navigation routes through `NavigationService`. The declared model is deliberately
**not** shown here: `Header.Model` is an ordinary enum field, edited in the Editor
like any other parameter.

### Tree pane

The tree contains BPX objects only, never individual parameters. Selecting an
object updates the parameter list. Validation markers appear on the lowest visible
object containing an issue; ancestors do not duplicate the marker once the branch
is open.

The tree is also where document *structure* is edited, via a right-click menu on
the node it lands on. The schema fixes the hierarchy, so the menu offers only its
real degrees of freedom — nothing disabled, nothing invented:

- **Add section ▸** lists the schema-expected child sections absent from the node
  (right-clicking empty space addresses the document root — how the optional
  top-level State/Validation are added).
- **Add material… / Add experiment…** appear on the two dict-keyed containers
  whose children the user names, via an anchored name popup (Enter confirms; a
  duplicate name is refused inline).
- **Add subsection…** appears on the open `User-defined` bucket and any subsection
  within it — the one place the schema lets the user name sections freely, nested
  without limit; user-authored sections carry a plain **· custom** tag.
- **Rename…** appears only on user-named object nodes (materials, Validation runs,
  User-defined subsections) — schema property names are never editable.
- **Remove / Remove section** covers everything structurally removable, required
  sections included (the validator reports the damage); removing populated content
  asks first, an empty target removes instantly, either is one undo step.

Free-form *parameters* are added via the parameter list's **+ Add parameter**, not
the tree menu.

### Parameter list pane

Shows the direct parameters of the selected object; selecting one updates the
Inspector. Each row carries a right-aligned, fixed-pitch **value preview** —
verbatim committed values, a ghosted "—" for `null`, a ghosted summary for
Inspector-only kinds ("table · 3 points"). The preview is deliberately
**read-only**: editing stays in the Inspector's per-kind cards.

A **+ Add parameter** header opens a popup for adding a parameter to the selected
object; actions on an *existing* row (**Rename…**, **Duplicate**, **Move
up/down**, **Remove parameter**) live in that row's right-click menu. This is the
app-wide convention: **context menus never create at row level, only at container
level** (the tree's Add section/material/experiment/subsection); creation is
offered by visible affordances. Move and Remove are offered for every real row;
Rename…/Duplicate are gated by `structure.can_rename_parameter` /
`can_duplicate_parameter` (user-named keys, plus any parameter whose alias the BPX
schema defines nowhere).

Creating a custom parameter is typed: the popup's fallback form takes Name + Unit
and one of five value types (scalar, text, boolean, table, series), each seeded
with a neutral empty value — the type *is* the stored value's shape, re-derived on
load, so changing it later means remove and re-add. A custom parameter's card
header carries a pencil that edits its Name/Unit in place; a schema-defined field
gets no pencil and its unit tooltip reads "Fixed by the BPX schema".

A row whose committed value is `null` renders muted/grey so emptiness reads at a
glance. A trailing severity dot (red = error, amber = warnings only) mirrors the
Diagnostics page's post-absorption Issues: an Expected field's calmed `null`
renders grey with no dot; a custom parameter's uncalmed `null` renders grey
**with** a dot. A collapsed
**`▸ N fields to add`** line sits at the end of the real rows whenever the section
has schema-Expected fields absent from the document; expanding it lists each
missing alias as an addable `+ name` row.

### Inspector pane

The Inspector is the selected parameter's work surface and the primary home for
all parameter-centric tools. It is split top-to-bottom:

- a **primary editing area** at the top, hosting the value editor **Edit**
  controls; and
- a collapsible **secondary workspace** at the bottom — a tab strip over a
  collapsible panel — hosting parameter-centric tools. In current scope it
  contains the **Issues** and **Documentation** tabs; future tools (Analysis,
  References) are added as further tabs over the same selected `ParameterItem`,
  not as separate pages or activity-bar workspaces.

For bulk work on large values (tables, experiment series), the primary editing
area supports an **expanded editor**: an **Expand** action grows the grid to fill
the Inspector pane (the secondary workspace collapses to its tab strip), *within
the Inspector pane* — never a floating window — and **Collapse** restores the
compact card. The convention this sets: **in-place takeover is for editing;
floating dialogs are reserved for read-only visualisation.**

The secondary workspace is **workspace state, not parameter state**: its
expanded/collapsed state, active tab and panel height persist across parameter
changes, refreshing the active tab's content rather than opening/closing on
selection. It collapses automatically only when no parameter is selected;
otherwise only the user collapses it.

**Parameter documentation is split by depth.** The card's ( i ) affordance opens a
transient **popover** for the quick glance (symbol, meaning, units, accepted
types, ontology link), destroyed with its card. The secondary workspace's
**Documentation** tab carries the multi-paragraph technical prose, persisting
beside the editor. Both are fed by the unified parameter-metadata provider (see
[01-architecture.md](01-architecture.md)).

### Diagnostics page

The Diagnostics workspace is a summary strip over a fixed-width section rail
beside a detail pane. `core/page_buckets.py` supplies the one shared grouping the
strip, rail and pane all render from, so they cannot disagree.

- The **strip** shows error/warning/outstanding totals; each chip is also a
  view-only filter toggle, and a text field filters rows live by case-insensitive
  substring. Filtering never changes any count anywhere (strip totals, rail
  badges, box headers and the app badge always report unfiltered truth); a muted
  "N hidden by filters" line accounts for what the filters hid. Filter state is
  per-session and resets on a new document.
- The **rail** lists "All sections" (the default) then one entry per section — in
  document order, present or not — with a Document bucket first when occupied.
  Badges are quiet: a clean section shows none; red/amber count badges appear only
  for nonzero errors/warnings; a grey badge marks outstanding work; an absent
  section renders its name italic.
- The **detail pane** is either one selected section's **Issues** and
  **Outstanding** group boxes, or — for "All sections" — the whole-document backup
  view: every bucket exactly once, foldable, so nothing can go missing between the
  two views.

Selecting a rail entry is pure page navigation and never touches the document. The
activation contract is shared with the Issues tab: **select ≠ act**;
Enter/double-click navigates.

### Status bar

Communicates document-level state such as source and modified/saved status,
keeping persistent file state out of the top context bar.

### Toolbar

The top bar carries document identity on the left and, on the right, only:
**Save** (writes back to the current backing file), **Export** (a menu offering
**Export as JSON…** / **Export as YAML…**, each writing a copy to a chosen path in
that format), **Undo**, **Redo**, and **Search**. It carries no Open/Import
action — opening a file lives on the Workspace page's **Open File** button.

**Undo** reverts the last committed change and navigates to the change it
reverted; greyed when there is nothing to revert. The toolbar button is a document
action and ignores keyboard focus. `Ctrl+Z` is bound separately and is
focus-aware: it undoes a focused text editor's own typing first, does nothing
while a focused card holds an uncommitted draft, and undoes the document
otherwise. **Redo** mirrors Undo, with `Ctrl+Y` (and `Ctrl+Shift+Z` where not
already a platform Redo binding). Unimplemented future actions do not appear as
disabled buttons.

## Navigation Model

All navigation is coordinated by the single `NavigationService`, whose contract
(resolve path → update state → emit one notification) is defined in
[01-architecture.md](01-architecture.md). On each navigation notification, views
collectively:

- expand the tree to the destination object and select it;
- select the parameter when the target is parameter-level;
- update the context bar;
- scroll the relevant destination into view;
- apply a temporary highlight to the destination.

Each view owns the reveal of its own part of the target; no component implements
its own competing navigation. Feature consumers (Search, Diagnostics review,
future Compare and reference links) request navigation by target path and never
drive widgets directly.

## Interaction Principles

These constrain every feature equally:

- Search and validation navigation must use `NavigationService`.
- Search navigates; it does not filter or hide structure.
- Guidance (validation, and later completion) informs; it does not lock the
  editor.
- Invalid edits may be committed to the raw working document.
- Parameter-centric tools are tabs in the Inspector secondary workspace, not
  activity-bar workspaces.
- The navigable BPX structure is never filtered — including by document
  ownership; ownership is shown through indicators, not by hiding hierarchy.
  Filtering applies only to derived views (Issues, Search results, Analysis).
- UI controls appear when their workflows exist, not as disabled placeholders.
- Creation is offered by visible affordances; actions on an existing row or node
  (remove, rename) are offered by that row's context menu.

## Keyboard Conventions

- Transient UI closes on Escape before state is cleared or focus returns.
- Enter commits the active editor card; Escape reverts its uncommitted draft.
- Search is focused by both `Ctrl+F` and `Ctrl+P`, and focusing search selects
  existing text.
- Popups anchored to a triggering control (SearchPopup, the add-parameter popup)
  follow the same pattern: Down/Up move the selection, Enter activates, Escape is
  staged (clears typed text first, then closes the popup).
- **Dismissal is uniform across every transient popup** (SearchPopup, the
  add-parameter popup, the parameter information popover). A mouse press outside
  the popup dismisses it, and that press is **consumed** — it does not reach the
  control beneath, so one click closes and a second click acts. Application
  deactivation also dismisses. A press *inside* the popup, or inside a control it
  declares as its own, neither dismisses nor is consumed. Dismissal is
  deliberately not driven by keyboard focus alone: focus does not move when the
  user presses a non-focusable surface such as the top bar, so a focus-driven rule
  would leave popups stranded open.
