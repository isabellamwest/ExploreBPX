# Explore_BPX — UI Framework

This document defines the **application-wide UI framework**: the shell layout,
the responsibilities of each pane, the global navigation model, common
interaction principles and keyboard conventions, and the global constraints every
feature must follow.

It deliberately does **not** describe individual feature behaviour. How a specific
feature behaves within this framework — the SearchPopup, the editing cards,
keyboard navigation of issues, the Issues tab, authoring workflows — lives with that
feature in [03-features.md](03-features.md). Architectural boundaries and the
navigation service contract live in [01-architecture.md](01-architecture.md).

Design rationale is embedded inline with the decision it explains.

## UI Philosophy

Explore_BPX presents a fixed, familiar editor-style shell rather than a wizard or
dashboard. The product-level philosophy is stated in [00-project.md](00-project.md);
its UI consequences are:

- BPX objects and parameters remain visible as a stable hierarchy.
- Search and validation navigate to locations; they never filter or replace the
  structure.
- Secondary information is available on demand without permanently occupying
  workspace.
- Editing works against the raw working document, so invalid work-in-progress
  data can be represented and corrected.

## Workspace Layout

The workspace uses a fixed multi-pane shell with familiar editor conventions:

```text
[top context bar spans the main content area]
[activity bar] | Tree | Parameter list | Inspector
[bottom status bar]
```

The main Editor workspace is a three-pane master-detail-detail layout:

- **Tree** — navigable BPX objects.
- **Parameter list** — the direct parameters of the selected object.
- **Inspector** — the selected parameter's workspace for viewing and editing.

All three panes remain visible while editing, so sibling context is preserved. A
selected object does not replace the tree, and a selected parameter does not
replace the parameter list.

**Rationale.** A fixed three-pane master-detail shell keeps object → parameter →
editor context visible at once and matches familiar IDE conventions, giving each
band one clear job. The alternatives — a two-pane body-swap, a dockable
inspector, or a floating document-info card — either hide sibling context or add
layout complexity without benefit. The cost is horizontal-space pressure from
three columns and a top bar that shows location rather than acting as clickable
navigation. The activity bar and Inspector are the seams that absorb future
workspaces and parameter-centric tools without reworking this layout.

## Panes and Shell Surfaces

### Activity bar

The activity bar switches the full content area between top-level workspaces. It
is a narrow (48px) VS Code-style icon rail: each entry is a monochrome outline
glyph with no visible text, and its name is discoverable via a hover tooltip
(and exposed to accessibility tools). The current workspaces are:

- **Editor** — the main tree/list/inspector workspace. It renders the current
  *Workspace* (see [00-project.md](00-project.md)); today that is always a single
  document, and it grows to render a Primary and optional Reference document
  additively rather than switching into a separate compare mode.
- **Validation** — a full issue list for the active document.

The Validation icon carries no colour or symbol of its own — no tick, no
warning triangle — since it must assert neither pass nor fail. A small pill
badge at its bottom-right corner carries that state instead: it shows the
combined error+warning count, and is coloured red only when at least one
*error* is present and amber when the document has warnings but no errors. An
issue-free document shows no badge at all. The activity bar otherwise uses no
colour: the selected entry is distinguished only by a left accent stroke and
a stronger icon tone: a design habit followed throughout the shell (see
[00-project.md](00-project.md)) to keep colour reserved for validity state.

The activity bar is reserved for **major workspaces that replace the main content
area**, such as Editor, Validation, and future **Workspace** (document- and
workspace-level information and management) and Database workspaces. Comparison is
deliberately **not** a separate activity-bar workspace: it is a capability of the
Editor when a Reference document is present, not a mode. Parameter analysis,
documentation, graphs, statistics and similar secondary tools
are **not** activity-bar workspaces; they belong in the Inspector. Only shipped
workspaces appear; disabled placeholders for future workspaces are not shown.

**Rationale.** Most future workspaces are full-area pages, so a vertical rail
scales better than top tabs and gives validation state a natural badge home. Top
tabs, a VS Code-exact sidebar-only switch, or menu-driven switching were rejected
as less scalable or less honest. The cost is relatively heavy chrome for only two
current workspaces and the need for an icon set. Workspace and Database can later
be added without layout rework.

### Page header

A 34px bar sits above the workspace stack (spanning the content column only,
never the activity bar itself) and shows the active page's name in small
upper-case type. It exists because the activity bar's entries lost their
visible text when they became icon-only buttons — the header is now the one
place the page's name is written out, and it always reflects whichever entry
is currently selected.

### Top context bar

The top bar communicates the current context: the file name and current location.

The top bar is a context surface, **not** a duplicate clickable breadcrumb; the
always-visible tree and parameter list already provide structural navigation. It
does not host feature modes — the application deliberately avoids modes, keeping
the editor spatially stable and routing all navigation through `NavigationService`
(see [01-architecture.md](01-architecture.md)).

### Tree pane

The tree contains BPX objects only, never individual parameters. Selecting an
object updates the parameter list. Validation markers in the tree appear on the
lowest visible object containing an issue; ancestors do not duplicate the marker
once the relevant branch is open.

### Parameter list pane

The parameter list shows the direct parameters of the selected object. Selecting a
parameter updates the Inspector. A **+ Add parameter** header sits above the list,
scoped to the currently selected object: it is enabled only when a document is
loaded and the selection can hold parameters, and it opens a small transient popup
anchored under the button for adding a parameter to that object — the pane's only
add-parameter surface, since the app deliberately has no context menus.

### Inspector pane

The Inspector is the selected parameter's work surface and the primary home for
all parameter-centric tools. It is split top-to-bottom into two areas:

- a **primary editing area** at the top, hosting the value editor **Edit**
  controls; and
- a collapsible **secondary workspace** at the bottom — a tab strip over a
  collapsible panel — hosting parameter-centric tools. In current scope it
  contains the **Issues** tab; future workflows (Analysis, References) are added
  as further tabs over the same selected `ParameterItem`, not as separate pages
  or activity-bar workspaces. Parameter *documentation* is deliberately not a
  secondary-workspace tab: contextual "what is this parameter?" help is delivered
  by an on-demand information popover anchored to the ParameterCard (see
  [Parameter information popover](#parameter-information-popover)).

A vertical splitter sits **above** the tab strip, so dragging it resizes the
whole secondary workspace (tabs and panel together). The secondary workspace is
**workspace state, not parameter state**: it starts collapsed, its tab strip is
always visible, and its expanded/collapsed state, active tab and panel height
persist across parameter changes. Only the user collapses it (by clicking the
active tab); selecting a different parameter refreshes the active tab's content
without opening or closing the workspace. The intended interaction is: click
Issues to open the panel, then click Issues again to collapse it.

**Rationale.** Secondary information should be reachable on demand without
permanently occupying workspace. Keeping parameter-centric tools in the Inspector
prevents activity-bar sprawl, preserves horizontal editing space, and keeps those
tools next to the parameter they describe. A single collapsible secondary
workspace with tabs — rather than a right-side dock or a stack of inline
accordion sections — keeps the tools together and their open/closed state simple
and predictable. Putting every feature in the activity bar, splitting Edit and
secondary tools into separate Inspector pages, or adding a permanent auxiliary
side panel were all rejected as cluttering or context-losing. The cost is that
expand/collapse and persisted workspace state need clear ownership in the UI
shell.

#### Parameter information popover

Rich BPX documentation for the selected parameter — its physical meaning, units,
accepted types, functional dependence, model availability, measurement methods,
specification links and symbols — is surfaced on demand through an information
popover triggered by an ( i ) affordance on the ParameterCard, not through a
secondary-workspace tab. The popover is transient: it opens from the card, closes
on a second ( i ) click or Escape (consistent with the keyboard conventions
below), and keeps the card itself visually clean. Its content is fed by a unified
parameter-metadata provider (see the seam in [01-architecture.md](01-architecture.md));
the feature and its supporting self-contained-card refactor are specified in
[03-features.md](03-features.md) and scheduled in [04-roadmap.md](04-roadmap.md).

### Status bar

The bottom status bar communicates document-level state such as source and
modified/saved status. This keeps persistent file state out of the top context
bar, whose role is location and mode.

### Toolbar

The toolbar remains minimal and fixed. Its current actions are:

- **Import** — a menu; current scope exposes Open File only.
- **Save** — writes back to the current backing file.
- **Export** — writes a copy to a chosen path/format.
- **Search** — global object/parameter navigation.

Unimplemented future actions do not appear as disabled buttons.

**Rationale.** A minimal, honest toolbar keeps controls meaningful; disabled
future buttons and conflated actions were rejected. Import is the seam through
which future sources (templates, databases, recent files) are added; Export is the
seam that later generalises to simulator hand-off. The precise semantics of Save
versus Export are a feature concern, specified in the Save and Export section of
[03-features.md](03-features.md).

**Future direction (not yet scheduled).** As the application becomes
Workspace-centred, the toolbar is expected to become *contextual* — exposing the
actions of the current activity-bar page rather than a fixed global set
(Workspace: Open, New, Recent, Settings; Editor: Save, Export, Undo, Redo,
Search), so opening a file becomes a Workspace action rather than an Editor
action. This is accepted as a principle only; its design must first reconcile how
a contextual toolbar relates to the top context bar and the added friction of
opening a second file from within
the Editor. It remains future design in [05-future.md](05-future.md).

## Navigation Model

All navigation is coordinated by the single `NavigationService`, whose service
contract (resolve path → update state → emit one notification) is defined in
[01-architecture.md](01-architecture.md). This section defines the **UI side**: how
views react to a navigation notification.

On each navigation notification, views collectively:

- expand the tree to the destination object and select it;
- select the parameter when the target is parameter-level;
- update the context bar;
- scroll the relevant destination into view;
- apply a temporary highlight to the destination.

Each view owns the reveal of its own part of the target; no component implements
its own competing navigation behaviour. Feature consumers (Search, Validation
review, and future Compare and reference links) request navigation by target path
and never drive widgets directly.

## Interaction Principles

These principles constrain every feature equally:

- Search and validation navigation must use `NavigationService`.
- Search navigates; it does not filter or hide structure.
- Guidance (validation, and later completion) informs; it does not lock the
  editor.
- Invalid edits may be committed to the raw working document.
- Parameter-centric tools are tabs in the Inspector secondary workspace, not
  activity-bar workspaces.
- The navigable BPX structure is never filtered — including by document
  ownership; ownership is shown through indicators, not by hiding hierarchy.
  Filtering applies only to derived views (Issues, Search results, Analysis
  summaries, future comparison reports), which interpret the structure rather
  than define it.
- UI controls appear when their workflows exist, not as disabled placeholders.

## Keyboard Conventions

Keyboard behaviour follows common desktop conventions. The framework-level
conventions are:

- Transient UI closes on Escape before state is cleared or focus returns.
- Enter commits the active editor card; Escape reverts its uncommitted draft.
- Search is focused by both `Ctrl+F` and `Ctrl+P`, and focusing search selects
  existing text.
- Popups anchored to a triggering control (SearchPopup, the add-parameter popup)
  follow the same pattern: Down/Up move the selection, Enter activates it, Escape
  is staged (clears typed text first, then closes the popup), and losing focus
  also dismisses the popup.

Feature-specific keys (search result navigation, keyboard navigation of issues)
are specified with their feature. As the UI matures, focus order and screen-reader
naming should be checked for the activity bar, SearchPopup, the issue lists and
editor cards.
