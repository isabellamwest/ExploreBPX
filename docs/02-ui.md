# Explore_BPX — UI Framework

This document defines the **application-wide UI framework**: the shell layout,
the responsibilities of each pane, the global navigation model, common
interaction principles and keyboard conventions, and the global constraints every
feature must follow.

It deliberately does **not** describe individual feature behaviour. How a specific
feature behaves within this framework — the SearchPopup, the editing cards,
keyboard navigation of issues, the Issues tab, authoring workflows — lives with that
feature in [03-features.md](03-features.md). Architectural boundaries and the
navigation service contract live in [01-architecture.md](01-architecture.md).

Design rationale is embedded inline with the decision it explains.

## UI Philosophy

Explore_BPX presents a fixed, familiar editor-style shell rather than a wizard or
dashboard. The product-level philosophy is stated in [00-project.md](00-project.md);
its UI consequences are:

- BPX objects and parameters remain visible as a stable hierarchy.
- Search and validation navigate to locations; they never filter or replace the
  structure.
- Secondary information is available on demand without permanently occupying
  workspace.
- Editing works against the raw working document, so invalid work-in-progress
  data can be represented and corrected.

## Workspace Layout

The workspace uses a fixed multi-pane shell with familiar editor conventions:

```text
[top context bar spans the main content area]
[activity bar] | Tree | Parameter list | Inspector
[bottom status bar]
```

The main Editor workspace is a three-pane master-detail-detail layout:

- **Tree** — navigable BPX objects.
- **Parameter list** — the direct parameters of the selected object.
- **Inspector** — the selected parameter's workspace for viewing and editing.

All three panes remain visible while editing, so sibling context is preserved. A
selected object does not replace the tree, and a selected parameter does not
replace the parameter list. The panes sit flush against one another, separated
by a single 1px hairline seam (the splitter handle itself) rather than a
gutter plus a bordered pane edge.

**Rationale.** A fixed three-pane master-detail shell keeps object → parameter →
editor context visible at once and matches familiar IDE conventions, giving each
band one clear job. The alternatives — a two-pane body-swap, a dockable
inspector, or a floating document-info card — either hide sibling context or add
layout complexity without benefit. The cost is horizontal-space pressure from
three columns and a top bar that shows location rather than acting as clickable
navigation. The activity bar and Inspector are the seams that absorb future
workspaces and parameter-centric tools without reworking this layout.

## Panes and Shell Surfaces

### Activity bar

The activity bar switches the full content area between top-level workspaces. It
is a narrow (48px) VS Code-style icon rail: each entry is a monochrome outline
glyph with no visible text, and its name is discoverable via a hover tooltip
(and exposed to accessibility tools). The current workspaces are:

- **Workspace** — document-level information and management: opening a file,
  creating a new document from a model skeleton, and current-document info. It
  is the app's default landing page when nothing is open.
- **Editor** — the main tree/list/inspector workspace. It renders the current
  *Workspace* (see [00-project.md](00-project.md)); today that is always a single
  document, and it grows to render a Primary and optional Reference document
  additively rather than switching into a separate compare mode.
- **Validation** — the active document's Issues and Outstanding (completion)
  lists (see [Validation page](#validation-page) below).

The Validation icon carries no colour or symbol of its own — no tick, no
warning triangle — since it must assert neither pass nor fail. A small pill
badge at its bottom-right corner carries that state instead: it shows the
combined error+warning count of the Validation page's **Issues** section
only (see [Validation page](#validation-page) below) — a diagnostic the page
has absorbed into its Outstanding section, because it is already covered
there, never contributes to the badge, and a single value's `float_type`/
`int_type` diagnostic pair counts once, matching the one row it renders as.
It is coloured red only when at least one *error* is present and amber when
the document has warnings but no errors. A fresh skeleton, or a document
whose only gaps are expected fields the app itself added and left empty,
shows no badge at all: **red means wrong, never unstarted**. The activity
bar otherwise uses no
colour: the selected entry is distinguished only by a left accent stroke and
a stronger icon tone: a design habit followed throughout the shell (see
[00-project.md](00-project.md)) to keep colour reserved for validity state.

The activity bar is reserved for **major workspaces that replace the main content
area**, such as Workspace, Editor, Validation, and a future Database workspace.
Comparison is deliberately **not** a separate activity-bar workspace: it is a
capability of the Editor when a Reference document is present, not a mode.
Parameter analysis, documentation, graphs, statistics and similar secondary tools
are **not** activity-bar workspaces; they belong in the Inspector. Only shipped
workspaces appear; disabled placeholders for future workspaces are not shown.

**Rationale.** Most future workspaces are full-area pages, so a vertical rail
scales better than top tabs and gives validation state a natural badge home. Top
tabs, a VS Code-exact sidebar-only switch, or menu-driven switching were rejected
as less scalable or less honest. The cost is relatively heavy chrome for only
three current workspaces and the need for an icon set. Database can later be
added without layout rework.

### Page header

A 34px bar sits above the workspace stack (spanning the content column only,
never the activity bar itself) and shows the active page's name in small
upper-case type. It exists because the activity bar's entries lost their
visible text when they became icon-only buttons — the header is now the one
place the page's name is written out, and it always reflects whichever entry
is currently selected.

### Top context bar

The top bar communicates the current document's identity: an elided label
reading `Title · BPX vX.Y` (either segment omitted when absent; the full text
is always available as a tooltip).

The declared model is deliberately **not** shown here. `Header.Model` is an
ordinary enum field, edited in the Editor like any other parameter — its
commit routes through `ChangeModel`, which also adds the target model's
required-but-missing sections in the same undo step (see
[Editing](03-features.md#4-editing)). An earlier build carried a Model chip in
this bar, a menu button that committed the same field; it was removed as a
second door onto an edit the Editor already offers, and because a per-document
field does not belong in the window's chrome.

The top bar is a context surface, **not** a duplicate clickable breadcrumb; the
always-visible tree and parameter list already provide structural navigation. It
does not host feature modes — the application deliberately avoids modes, keeping
the editor spatially stable and routing all navigation through `NavigationService`
(see [01-architecture.md](01-architecture.md)).

### Tree pane

The tree contains BPX objects only, never individual parameters. Selecting an
object updates the parameter list. Validation markers in the tree appear on the
lowest visible object containing an issue; ancestors do not duplicate the marker
once the relevant branch is open.

The tree is also where document *structure* is edited, via a right-click menu
on the node it lands on. The schema fixes the hierarchy, so the menu offers
only its real degrees of freedom — nothing disabled, nothing invented:
**Add section ▸** lists the schema-expected child sections absent from the
node (right-clicking empty space addresses the document root, which is how the
optional top-level State/Validation are added; the electrode sections resolve
their single/blended union from the electrode's own live content, rather than
guessing). **Add material… /
Add experiment…** appear on the two dict-keyed containers whose children the
user names, opening a small anchored name popup (Enter confirms; a sibling's
name is refused with the reason inline). **Rename…** appears only on
user-named keys — materials and Validation runs; schema property names are
never editable — pre-filled with the current name, and confirming it unchanged
is a silent no-op. **Remove / Remove section** covers everything structurally
removable, required sections included (the validator reports the damage);
removing a *populated* target asks first, an empty one removes instantly, and
either is one undo step.

### Parameter list pane

The parameter list shows the direct parameters of the selected object. Selecting a
parameter updates the Inspector.

Each row carries a right-aligned **value preview** in a smaller fixed-pitch
face: simple committed values verbatim from the raw document (JSON spelling,
never reformatted or rounded), a ghosted "—" for a committed `null`, and a
ghosted, data-derived summary for Inspector-only kinds ("table · 3 points",
"2 entries", "series · 60 values"). The preview never claims more than ~45%
of the row — an overlong mantissa elides with "…" and the full value is on
the row's tooltip. The preview is deliberately **read-only**: a 2026-07-15
design pass on inline quick inputs concluded the scanning value lay in seeing
values, not in a second editing surface — editing stays in the Inspector,
whose per-kind cards already carry the commit grammar. A **+ Add parameter** header sits above the list,
scoped to the currently selected object: it is enabled only when a document is
loaded and the selection can hold parameters, and it opens a small transient popup
anchored under the button for adding a parameter to that object. The
button is a shaded, inset control (not a native full-bleed button) with even
padding around it, and reads as honestly unavailable — greyed, not error-toned —
while disabled.

Creation lives in this always-visible header affordance; actions on an
*existing* row — such as **Remove parameter** — live in the row's right-click
context menu. That split is the app-wide convention: context menus never
create **at row level**, and creation of parameters is never hidden behind a
right-click — but they *do* create at container level (the tree's
**Add section ▸ / Add material… / Add experiment…**), because sections and
dict-keyed collections are the containers being filled.

A row whose committed value is `null` renders muted/grey — name and unit
both — so emptiness is visible at a glance, whether the field has never been
filled or its value was deliberately cleared (the raw dict cannot tell those
apart, so the row does not pretend to). The trailing **⚠** marker means a
*page-visible* Issue — the same set the Validation page's Issues section
shows — not the validator's raw, unabsorbed output: an Expected field's own
`null` is calmed by completion (see [Validation](03-features.md#5-validation)
and [Authoring](03-features.md#8-authoring)), so it renders grey with no ⚠,
while a *custom* parameter's `null` stays uncalmed (its `extra_forbidden`
rejects the name, not the emptiness) and renders grey **with** ⚠. A
parameter's own Inspector card badge and Issues tab are unaffected by this —
they report the validator verbatim regardless of what the list row shows.

A collapsed line, **`▸ N fields to add`** (singular "field" when `N` is 1),
sits at the end of the real rows whenever the selected section has schema
Expected fields with no entry in the document — every expected alias, not
Required-only, so an optional expected field is offered too. It is closed by
default; clicking it, or a row already selected plus Enter, toggles it open
to `▾ N fields to add` and lists each missing alias as a compact `+ name`
row, styled and tagged exactly like the add-parameter popup's own Suggested
rows (a `REQUIRED` tag under a concrete model; none under `Partial`, where
suggestions still show but nothing is Required — see
[Authoring](03-features.md#8-authoring)). Clicking, or Enter on, a `+` row
adds that field with an honest `null` through the same `AddParameter`
command the popup uses, then reveals and focuses the new row's editor — one
undo step, the popup's Suggested path verbatim. **The group's expanded state
survives a rebuild of the same section** (every add commits a command, which
rebuilds the list), so adding several fields in a row keeps the group open;
navigating to a different section always shows a fresh, collapsed group. The
group is suppressed under an undeclared or unrecognised model — the one
visible completion task there is declaring a model, not a suggestion list
against a model nobody has picked yet — and whenever a section has no missing
fields at all (no "0 fields to add" placeholder). **`Header` is the one
exception to that suppression:** its fields (`Title`/`Model`/`BPX`) do not
vary by model, and its suggestion row for `Model` is where a model actually
gets declared, so Header's group shows even while the model is undeclared.

### Inspector pane

The Inspector is the selected parameter's work surface and the primary home for
all parameter-centric tools. It is split top-to-bottom into two areas:

- a **primary editing area** at the top, hosting the value editor **Edit**
  controls; and
- a collapsible **secondary workspace** at the bottom — a tab strip over a
  collapsible panel — hosting parameter-centric tools. In current scope it
  contains the **Issues** tab; future workflows (Analysis, References) are added
  as further tabs over the same selected `ParameterItem`, not as separate pages
  or activity-bar workspaces. Parameter *documentation* is deliberately not a
  secondary-workspace tab: contextual "what is this parameter?" help is delivered
  by an on-demand information popover anchored to the ParameterCard (see
  [Parameter information popover](#parameter-information-popover)).

For bulk work on large values (interpolated tables, experiment series), the
primary editing area supports an **expanded editor**: a text **Expand** action
on the grid's toolbar grows the grid to fill the Inspector pane (the secondary
workspace collapses to its tab strip to make room), *within the Inspector
pane* — never a floating window — and **Collapse** restores the compact card.
The tree and parameter list stay visible and interactive throughout. The
convention this sets: **in-place takeover is for editing; floating dialogs are
reserved for read-only visualisation** (see Analysis in
[03-features.md](03-features.md)).

A vertical splitter sits **above** the tab strip, so dragging it resizes the
whole secondary workspace (tabs and panel together). The secondary workspace is
**workspace state, not parameter state**: it starts collapsed, its tab strip is
always visible, and its expanded/collapsed state, active tab and panel height
persist across parameter changes. Selecting a different parameter refreshes the
active tab's content without opening or closing the workspace.

The workspace is nevertheless *scoped to a parameter*, so it collapses
automatically whenever no parameter is selected (the Inspector's placeholder
state); its tab strip stays visible. This changes visibility only — the user's
expand/collapse intent and active tab are remembered and restored as soon as a
parameter is selected again. Apart from that, only the user collapses it (by
clicking the active tab). The intended interaction is: click Issues to open the
panel, then click Issues again to collapse it.

**Rationale.** Secondary information should be reachable on demand without
permanently occupying workspace. Keeping parameter-centric tools in the Inspector
prevents activity-bar sprawl, preserves horizontal editing space, and keeps those
tools next to the parameter they describe. A single collapsible secondary
workspace with tabs — rather than a right-side dock or a stack of inline
accordion sections — keeps the tools together and their open/closed state simple
and predictable. Putting every feature in the activity bar, splitting Edit and
secondary tools into separate Inspector pages, or adding a permanent auxiliary
side panel were all rejected as cluttering or context-losing. The cost is that
expand/collapse and persisted workspace state need clear ownership in the UI
shell.

#### Parameter information popover

Rich BPX documentation for the selected parameter — its physical meaning, units,
accepted types, functional dependence, model availability, measurement methods,
specification links and symbols — is surfaced on demand through an information
popover triggered by an ( i ) affordance on the ParameterCard, not through a
secondary-workspace tab. The popover is transient: it opens from the card and
closes on Escape, on a press outside it (which is consumed — see the keyboard and
dismissal conventions below), on application deactivation, or on a second ( i )
click. It is destroyed with its card, so changing the inspected parameter cannot
leave it describing the wrong one. It keeps the card itself visually clean and
never obscures the parameter it documents. Its content is fed by a unified
parameter-metadata provider (see the seam in [01-architecture.md](01-architecture.md));
the feature and its supporting self-contained-card refactor are specified in
[03-features.md](03-features.md) and scheduled in [04-roadmap.md](04-roadmap.md).

### Validation page

The Validation activity-bar workspace is a single list, split into two
always-present sections, **Issues** above **Outstanding** — see
[Validation](03-features.md#5-validation) for the absorption rule and
badge-derivation architecture behind the split. Each section starts with a
**labelled divider** — a hairline rule carrying the bold section title
(`── Issues ────`) and a muted count suffix (`· 7 errors · 1 warning`,
`· 4 remaining`, omitted when the section is empty) — so the page's scale
reads before any row detail; neither header is selectable.

Only actionable rows (an issue, an Outstanding task) show hover or selection
highlight. Headers, group rows, empty-state messages and spacers paint flat
wherever the mouse is — a highlight promises interaction, and activating
those rows does nothing. The foldable group headers are still clickable;
their chevron is the affordance.

**Issues** lists every validator diagnostic not already accounted for by an
Outstanding task, **clustered into collapsible groups by section**. A group
header reads `▾ <Section>  N` (`N` coloured by the group's worst severity);
a single click folds it away — the navigation aid for a document with many
issues, and a fold survives later edits. Each issue row is **two lines**: a
coloured severity tag (`ERROR` red / `WARN` amber) and the bold,
section-relative location on the first (its trailing unit muted), the
validator's verbatim message on the muted second — so *where* and *what* stop
sharing one run-on line. A diagnostic with no location clusters under a
`Document` group. A single bad `FloatInt` value's paired diagnostics — both
the wrong-type (`float_type`/`int_type`) and the bad-string
(`float_parsing`/`int_parsing`) variants — render as one row here
(display-only de-duplication; the validator's own output is untouched). An
empty section shows `✓ No issues`.

**Outstanding** lists the document's completion tasks, grouped by owning
section in document order. A section renders up to two bold, muted
subheaders — like the Issues groups, each is **foldable with a single click**
(chevron-marked, never selectable), and the two sub-groups of one section
fold independently. Folds persist across edits but reset when a different
document is opened (fold state is per-document, keyed by section name):

- a **required** group, `<Section> — N of M remaining` (or `<Section> —
  section absent` for a section that does not exist yet), holding only
  Required tasks — `N` therefore always equals the row count beneath it;
- a quieter **optional** sub-group beneath it, `<Section> · optional — K
  unfilled`, for Expected-but-optional fields committed `null`.

Either may be absent — a section with only optional nulls shows no required
header at all, one with none shows no optional sub-group. A "Declare a
model" task (only ever the page's sole Outstanding entry, since nothing else
is knowable without a model) renders standalone with no subheader. Every row
names its own action, so nothing mutates without saying so:

| Row | Text | Action |
|---|---|---|
| Missing required field | `<alias>` `REQUIRED` | `Go to ›` |
| Field added but still `null` | `<alias> — added, no value yet` (`REQUIRED` tag only when the field is also Required) | `Go to ›` |
| Section not yet added | `<section name>` | `+ Add section` |
| Model not yet declared | `Declare a model` | `Choose…` |

Any row that stands in for real validator output shows it — never removed,
only re-seated (see [Validation](03-features.md#5-validation)): the row
carries its absorbed diagnostic's own message as a muted secondary line
beneath the row text, merging a `float_type`/`int_type` pair to one line the
same way the Issues section does. A field's `null` is Outstanding whenever
it is schema-Expected, Required or not — creating an expected field and
leaving it empty never makes the document look worse — but a **custom**
parameter (no schema entry at all) never gets an Outstanding row: its
`extra_forbidden` rejects the name, not the emptiness, so it stays a plain
Issue, and its parameter-list row is grey **with** a ⚠ (see
[Parameter list pane](#parameter-list-pane) above).

An empty Outstanding section shows `✓ Nothing outstanding`; under a `Partial`
model, where nothing is ever Required, it instead shows: *"Model is Partial —
no completion target. Expected fields are still suggested in each section's
parameter list."*

**Activation contract**, shared with the Issues tab and the rest of the app's
list-driven navigation: selecting a row (arrow keys or a single click) never
acts by itself; only Enter/Return or a double-click activates it. Header and
subheader rows are not selectable at all, so keyboard focus can never land on
one. Activating a row performs the action its own text names:

- an **Issue** row navigates to its location via `NavigationService`, like
  today;
- a **missing-field** row navigates to the *owning section* (the field has
  no address of its own yet), expands that section's parameter-list "fields
  to add" group, and highlights the row — it does not add the field; the
  group's own `+` does that;
- an **added-no-value** row navigates straight to the parameter, which
  already exists;
- an **absent-section** row adds the section and navigates into it, one undo
  step, since there is nothing to navigate to first;
- the **declare-a-model** row navigates to `Header` and reveals its `Model`
  suggestion row, ready to pick a model from the enum editor — the same
  motion as a missing-field row. When `Header.Model` is present but
  unrecognised it is a committed parameter rather than a suggestion, so the
  row navigates straight to it instead.

### Status bar

The bottom status bar communicates document-level state such as source and
modified/saved status. This keeps persistent file state out of the top context
bar, whose role is location and mode.

### Toolbar

The toolbar remains minimal and fixed. Its current actions are:

- **Import** — a menu; current scope exposes Open File only.
- **Save** — writes back to the current backing file.
- **Export** — writes a copy to a chosen path/format.
- **Undo** — reverts the last committed change and navigates to the change it
  reverted, rather than leaving the user wherever they happened to be; greyed
  when there is nothing to revert. The button is a document action and ignores
  keyboard focus.
  `Ctrl+Z` is bound separately and is focus-aware: it undoes a focused text
  editor's own typing first, does nothing while a focused card holds an
  uncommitted draft, and undoes the document otherwise (see the Editing section
  of [03-features.md](03-features.md)).
- **Redo** — mirrors Undo exactly: reapplies the most recently undone change
  and navigates to the change it reapplied; greyed when there is nothing to
  reapply. The button is a document action and ignores keyboard focus.
  `Ctrl+Y` (and `Ctrl+Shift+Z`, wherever that is not already the platform's
  own Redo binding) is bound separately and is focus-aware, mirroring `Ctrl+Z`
  (see the Editing section of [03-features.md](03-features.md)).
- **Search** — global object/parameter navigation.

Unimplemented future actions do not appear as disabled buttons.

**Rationale.** A minimal, honest toolbar keeps controls meaningful; disabled
future buttons and conflated actions were rejected. Import is the seam through
which future sources (templates, databases, recent files) are added; Export is the
seam that later generalises to simulator hand-off. The precise semantics of Save
versus Export are a feature concern, specified in the Save and Export section of
[03-features.md](03-features.md).

**Future direction (not yet scheduled).** As the application becomes
Workspace-centred, the toolbar is expected to become *contextual* — exposing the
actions of the current activity-bar page rather than a fixed global set
(Workspace: Open, New, Recent, Settings; Editor: Save, Export, Undo, Redo,
Search), so opening a file becomes a Workspace action rather than an Editor
action. This is accepted as a principle only; its design must first reconcile how
a contextual toolbar relates to the top context bar and the added friction of
opening a second file from within
the Editor. It remains future design in [05-future.md](05-future.md).

## Navigation Model

All navigation is coordinated by the single `NavigationService`, whose service
contract (resolve path → update state → emit one notification) is defined in
[01-architecture.md](01-architecture.md). This section defines the **UI side**: how
views react to a navigation notification.

On each navigation notification, views collectively:

- expand the tree to the destination object and select it;
- select the parameter when the target is parameter-level;
- update the context bar;
- scroll the relevant destination into view;
- apply a temporary highlight to the destination.

Each view owns the reveal of its own part of the target; no component implements
its own competing navigation behaviour. Feature consumers (Search, Validation
review, and future Compare and reference links) request navigation by target path
and never drive widgets directly.

## Interaction Principles

These principles constrain every feature equally:

- Search and validation navigation must use `NavigationService`.
- Search navigates; it does not filter or hide structure.
- Guidance (validation, and later completion) informs; it does not lock the
  editor.
- Invalid edits may be committed to the raw working document.
- Parameter-centric tools are tabs in the Inspector secondary workspace, not
  activity-bar workspaces.
- The navigable BPX structure is never filtered — including by document
  ownership; ownership is shown through indicators, not by hiding hierarchy.
  Filtering applies only to derived views (Issues, Search results, Analysis
  summaries, future comparison reports), which interpret the structure rather
  than define it.
- UI controls appear when their workflows exist, not as disabled placeholders.
- Creation is offered by visible affordances; actions on an existing row or
  node (remove, rename) are offered by that row's context menu.

## Keyboard Conventions

Keyboard behaviour follows common desktop conventions. The framework-level
conventions are:

- Transient UI closes on Escape before state is cleared or focus returns.
- Enter commits the active editor card; Escape reverts its uncommitted draft.
- Search is focused by both `Ctrl+F` and `Ctrl+P`, and focusing search selects
  existing text.
- Popups anchored to a triggering control (SearchPopup, the add-parameter popup)
  follow the same pattern: Down/Up move the selection, Enter activates it, and
  Escape is staged (clears typed text first, then closes the popup).
- **Dismissal is uniform across every transient popup** — SearchPopup, the
  add-parameter popup and the parameter information popover. A mouse press
  outside the popup dismisses it, and that press is **consumed**: it does not
  reach the control beneath, so one click closes and a second click acts. This is
  the convention menus and command palettes follow everywhere. Application
  deactivation also dismisses. A press *inside* the popup, or inside a control it
  declares as its own (the search box, for its results list), neither dismisses
  nor is consumed. Dismissal is deliberately not driven by keyboard focus alone:
  focus does not move when the user presses a non-focusable surface such as the
  top bar or the page header, so a focus-driven rule would leave popups
  stranded open.

Feature-specific keys (search result navigation, keyboard navigation of issues)
are specified with their feature. As the UI matures, focus order and screen-reader
naming should be checked for the activity bar, SearchPopup, the issue lists and
editor cards.
